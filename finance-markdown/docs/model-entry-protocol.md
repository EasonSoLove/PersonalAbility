# 模型交易录入协议

## 意图判断

只有用户明确要求“录入、写入、添加、更新、确认、修改、作废”时，模型才可以改变正式账本。用户只是要求“整理、识别、看看、分析”时，只生成预览，不提交。

## 自然语言转字段

1. 相对日期必须转换为绝对日期。
2. 历史截图或旧聊天中的“今天/昨天”无法确定时必须询问，不能按当前日期猜测。
3. 未提供的确认日期、确认份额、确认净值、手续费和实际到账保持为空。
4. 空值表示未知；`0` 表示确认数值为零，两者不能混用。
5. 基金代码必须标准化为六位，但不能根据基金名称猜一个不确定的代码。
6. 一次输入中的多笔交易必须全部进入同一个批次。

## 标准流程

1. 读取 `data/schema.json`、`data/funds.yaml` 和正式账本。
2. 生成 `inbox/batches/YYYY-MM-DD-NNN.csv`。
3. 运行导入程序但不加 `--commit`。
4. 检查新增、更新、作废、疑似重复和字段错误。
5. 对含糊内容先向用户确认，禁止用默认值掩盖信息缺失。
6. 用户意图明确且预检通过后，使用 `--commit` 原子导入。
7. 运行 `validate_data.py` 和 `generate_reports.py`。
8. 向用户报告正式写入的交易ID和仍待确认的字段。

## 更新待确认交易

优先通过交易ID定位。没有交易ID时，只能在申请日期、基金代码、交易类型、金额和份额组合能唯一匹配时更新；存在多个候选时必须询问。

## 疑似重复

同一申请日期、基金代码、交易类型、申请金额和确认份额与已有记录一致时，默认停止导入。只有用户明确确认确实是两笔不同交易，才允许绕过疑似重复保护。

## 安全边界

- 不直接删除正式账本中的历史行；
- 不手工填写持仓、成本、盈亏和现金流等派生值；
- 不覆盖历史分析报告；
- 不修改旧版 `finance` 文件夹；
- 导入失败时正式账本必须保持不变。
