# 企业 Agent 瓶颈与落地方法论

> 来源：知乎文章《企业Agent瓶颈》提炼总结

---

## 核心论点：两个世界的根本区别

**干净世界（Coding Agent）**：任务所有者=执行者，环境有客观裁判（编译器/测试用例），试错成本接近零（git revert）。

**脏世界（企业 Agent）**：业务方含糊的口头需求 → 脏数据上的具体动作。一头模糊，一头要求精确；一头延迟，一头要求实时；一头不可逆，一头要求可追责。

> Claude Code 和 Hermes 做的是 **干净→干净** 的翻译；企业 Agent 做的是 **脏→干净** 的翻译。这是两件根本不同的事，但所有 Agent 框架/paper 写的全是第一件事。

---

## 五堵墙（企业 Agent 必然面对的问题）

| # | 墙 | 核心矛盾 |
|---|-----|---------|
| 1 | **数据是脏的** | 扫描件、矛盾文件名、多版本并存，80% 的 Agent 项目死在这一层 |
| 2 | **半结构化数据** | 有格式但不严格，有结构但会破。正则解不动，LLM 看不全——"中间地带的诅咒" |
| 3 | **长上下文是伪命题** | 厂商标称 100M token 是找事实（needle-in-a-haystack），企业任务是多跳推理，有效窗口可能只有 8K-32K |
| 4 | **业务逻辑本身是模糊的** | "合理期限""明显标志"不是 bug，法律本身留解释空间 |
| 5 | **用户既要又要还要** | 准、快、便宜、简单四个互相矛盾的需求 |

## 四层系统工程（解法不在模型里）

解法 = **数据工程 + Harness + 业务工程 + 产品设计**，Harness 只是其中一层。

### 第一层：脏数据预处理管道 — 让 LLM 远离原始数据

**为什么不能直接喂多模态 LLM：**
- **黑盒**：拿不到中间产物，出事故无法解释"模型说的"站不住脚
- **不可复现**：无法重放事故现场，法律上举证失败
- **数据不沉淀**：用完就丢，其他部门无法复用

**正确做法：**
1. **文档解析**：专业库提文本+表格+图片，扫描件走 OCR 流水线，多模态 LLM 只留给手绘图/印章重叠等真正需要看图的场景
2. **结构化索引**：章节树、图表位置、交叉引用建成可查询图谱（不是塞向量库就完事）
3. **分级存储**：原文/摘要/索引各一份，LLM 永远不直接读原文，只通过索引定位片段

> **反共识点**：这层跟 LLM 没关系，是数据治理。是脏活累活，但做不好后面四层全是空谈。

### 第二层：混合解析 — 结构化的归规则，模糊的归 LLM

**确定字段（金额/日期/编号/当事人）→ 正则+解析器**：
- 100% 确定，零 token 消耗，可审计可回滚
- 把确定的交给 LLM = 把确定变不确定 + 可审计变不可审计 + 可维护变不可维护

**模糊文本（合理使用范围/隐式引用/推理条款）→ LLM**：
- 只给相关片段，不给全文
- 两路结果在索引层合并

> **一句话**：LLM 是用来吸收不确定性的，不是用来制造不确定性的。

### 第三层：长上下文治理 — 别迷信 100 万 token

**现实**：号称 128K 的模型做复杂推理任务时有效窗口只有 8K-16K，号称 1M 的也就 32K 上下。

**分治策略：**
1. 按章节/主题/条款拆成独立片段，每个控制在有效推理窗口内（经验值 8K-32K）
2. 每个片段配上引用上下文（引用了谁、被谁引用）— 这是**图**，不是树
3. 推理结果在顶层汇总，底层只做"这段是否符合标准 X"

> **反共识点**：Coding Agent 的读→改→测→提交是线性的（编译器兜底），企业文档互相引用但没有编译器。照搬线性 ReAct 循环，死循环是必然的。必须做**图遍历**。

### 第四层：模糊逻辑的规则化 — 让 LLM 做判断，不让 LLM 做定义

**错误做法**：把"合理"原封不动塞给 LLM → 不一致 + 不可解释 + 不可协商

**正确做法：**
1. 离线用 LLM 对每个模糊条款生成 3-5 个具体化判断标准（如"违约金合理" → "不超过合同金额 30%"）
2. 跟业务方一起 review，改到双方认可（**业务方必须在场**）
3. 审查时 Agent 只判断是否满足这些显式标准
4. 标准是配置化的、可版本化的、可追溯的

> **一句话**：让 LLM 做判断，不让 LLM 做定义。定义留给业务，判断交给模型。

### 第五层：用户预期管理 — 你卖的不是 Agent，是确定性

**三种模式共用同一套基础设施，区别只在调度策略：**

| 模式 | 策略 | 速度 | 覆盖率 |
|------|------|------|--------|
| 快速模式 | 粗筛+关键词+规则，不调 LLM | 秒级 | 80% |
| 标准模式 | LLM 逐条审查 | 分钟级 | 95% |
| 深度模式 | 多模型交叉验证+强制人工复核 | 小时级 | 99% |

> 用户真正要的不是又快又准又便宜，是**知道什么时候能拿到什么质量的结果**。

---

## 评估体系：没有标准答案，只有相对改进

| 方法 | 要点 |
|------|------|
| **和基线比** | 人工审一份多久？漏审率多少？Agent 快了 30% 就是有效果。90% 团队不做基线测量 |
| **量置信度，不量准确度** | 高风险揪出 80% 不误报，低风险自动放行不出错，中间老实标"建议人工复核" |
| **做盲测** | 历史案例 Agent 独立审查 vs 人审比对，不一致找第三方裁决。不做自评（同一模型审完自己打分） |
| **监控漂移** | 每月抽最新案例跑核心指标，法规/数据分布变化会导致能力漂移 |

---

## 向上汇报话术

- 数据层 → "我们在建公司的文档资产层，Agent 只是第一个消费者，法务/合规/审计后面都会用"（成本中心 → 基础设施）
- 可视化指标 → "已治理文档数/总文档数""可追溯字段覆盖率"（比技术指标好汇报）
- 业务口径知识 → "我们把法务部的隐性知识显性化了，新人入职第一天就能上手"（标准化 → 组织资产）

## 关键金句

1. 不是你水平不行，是那些方法论假设的前提，你的项目里一条都不成立
2. 80% 的 Agent 项目死在数据治理这一层
3. LLM 是用来吸收不确定性的，不是用来制造不确定性的
4. 让 LLM 做判断，不让 LLM 做定义
5. 你做的不是 Agent 产品，是确定性产品
6. 在脏世界里，相对改进就是一切
