# 电梯调度 = 带释放时间的一维 TSP

> 一个 1990 年就被证明「多项式可解、且只能 O(n²)」的问题，在 2026 年被人改进到了 **O(n log n)**。
> 本目录是这篇知乎文章的**代码复刻 + 正确性验证 + 复杂度实测 + 可视化**。
>
> 原文文本：[../../zhihu-article-raw.txt](../../zhihu-article-raw.txt)（原作者：知乎 @灵剑）

## 一句话版本

原本的状态是 `(x, y)`：左边推进到哪、右边还剩到哪 —— 平方级的组合。
作者发现**只有会「卡住」车的点才影响决策**，而那些点的组合数可以**裂项相消**塌成线性，
于是状态从 O(n²) 变成 O(n)，再挂个优先队列 Dijkstra，就是 **O(n log n)**。

## 记号表（读原文必备）

| 记号 | 全称 | 含义 |
|---|---|---|
| `P` | **P**osition / floor | 位置：第几层楼、路上的第几米 |
| `A` | **A**rrival time | 到达时间：这个人第几秒才出现、开始等车（也叫释放时间 release time） |
| `A − P` | — | 车从坐标 0 出发向右，到 `P` 时需要等多久的「累计量」 |
| `A + P` | — | 同一个东西的左右镜像，用来找右侧卡点 |
| `L` | left stuck points | 左侧卡点序列（从左往右扫时的「必须等待点」） |
| `R` | right stuck points | 右侧卡点序列（从右往左扫时的「必须等待点」） |
| `x` | — | 左侧卡点下标，越大越靠中间 |
| `y` | — | 右侧卡点下标，**从右往左编号**，越大越靠中间 |
| `x′` | 对侧卡点 | 右侧第一个「`A` 比 `A_x` 更晚」的卡点，是一条**安全线** |
| `S(x)` | stuck state | 卡在 `x` 上的所有状态里，`y` 最大的那个 |
| `n` | — | 卡点总数 `\|L\| + \|R\|`（`n ≤ m`，`m` 是不同位置数） |

> ⚠️ 最容易搞反的一点：`y` 是**从右往左**编号的，`y=0` 才是最右边、最远的那个。

## 问题定义

一条数轴，速度 1 的电梯/大巴，可任意掉头、等待。

请求 `i = (A_i, P_i)`：电梯在时刻 `t ≥ A_i` 且位于 `P_i` 时，请求被服务。

**目标：所有请求都被服务的最早时刻。** 只看「最后一个完成的时间」，不看每个人等了多久。

LeetCode: [`elevator-requests-iii`](https://leetcode.cn/problems/elevator-requests-iii/)（会员题）

## 基线：O(n²) 动态规划

**关键观察 1**：同一位置只保留最晚到的那个（早到的人跟着他一起上车，答案不变）。

**关键观察 2**：左边还有 A 没接、右边还有 B 没接时，A 和 B 中间的人可以假装都没上车 ——
因为车迟早要在 A 和 B 之间至少走一趟，顺路就接上了。

所以状态只要记**两个端点**：`(x, y)`。状态数 O(n²)，转移 O(1)，总 O(n²)。

---

## 三步优化到 O(n log n)

### 第一步：删掉对问题没贡献的点（找「卡点」）

车从最左端出发一路向右，遇到「人还没来」就得停 —— 这种位置叫**左侧卡点**。

判据：

```
A_i − P_i 严格大于左边所有点的 A_j − P_j     →  i 是左侧卡点
```

因为「到达 `P_i` 的时刻」正好是 `P_i + max_{j≤i}(A_j − P_j)`，
所以 `A_i − P_i` **刷新前缀最大值** ⟺ 到这儿必须等。扫一遍 O(m) 即可。

右侧同理，镜像判据是 `A_i + P_i` 从右往左的严格前缀最大值。

**为什么非卡点可以删？** DP 里人永远从两边往中间接；接某点时要么左边全接完、要么右边全接完。
若左边全接完还得等 → 它是左侧卡点；右边全接完还得等 → 右侧卡点；都不是 → 顺路接的，不用为它做决策。

### 第二步：合并「卡住」的状态 → `S(x)`

所有**卡在同一个点 `x`** 上的状态，等完之后出发的时刻**都是 `A_x`**（固定），
既然时间一样，那 `y` 越大越好（对面完成得更多）。

于是反向记录：`S(x)` = 能卡在 `x` 上的状态里 `y` 的最大值，**把一个维度消掉了**。

```python
stuck_left[x + 1] = max(stuck_left[x + 1], y)
```

### 第三步：去对端时折叠一整段 `y` → 对侧卡点 `x′`

这是全局最关键的一步。原来 `(x, y) → (y, x+1)` 每个 `y` 都要开新状态，平方级的来源。

定义：

```python
x′ = min{ j : R[j].A > L[x].A }      # 右侧第一个「到达时间更晚」的卡点
```

推理只有一行：`A_{x′−1} ≤ A_x`，而当前时刻 `≥ A_x`，所以

> **跑到 `x′−1` 之前的所有 `y`，全都已经在等了 → 全程不卡 → 一整段 `y` 合并成同一个状态 `(x′−1, x+1)`。**

剩下需要单独展开的只有 `y ∈ [x′, (x+1)′]`，而 `y > (x+1)′` **根本不可能**
（它比 `x+1` 还晚到，说明 `x+1` 早就完成了，不会卡在那儿）。

### 裂项相消

每个 `x` 只产生 `(x+1)′ − x′ + 2` 个新状态，对所有 `x` 求和：

```
Σ [ (x+1)′ − x′ ] = k′ − 0′        ← 只看首尾，中间全约掉
```

**总状态数 = O(n)**。挂上优先队列 Dijkstra（转移时时间单调递增，按时间出队即可），
每个状态一次二分查找 + 一次堆操作 = O(log n)，总计 **O(n log n)**。

## 实测（[bench_output.txt](bench_output.txt)）

`unimodal` 是让状态数最多的最坏形状：

| n | \|L\| | \|R\| | 实际访问状态数 | 出堆次数 | 耗时 |
|---|---|---|---|---|---|
| 1,000 | 501 | 500 | 1,242 | 1,747 | 2.7 ms |
| 10,000 | 5,001 | 5,000 | 12,492 | 17,497 | 34.1 ms |
| 100,000 | 50,001 | 50,000 | **124,992** | 174,997 | **428 ms** |

`n` 涨 100 倍，状态数只涨 100 倍 —— 线性 ✅

与「不合并的诚实版 O(n²)」对比：

| n | 作者算法状态数 | O(n²) 状态数 | 倍数 |
|---|---|---|---|
| 200 | 242 | 15,782 | 65× |
| 500 | 617 | 95,732 | 155× |
| 1,000 | 1,242 | 378,982 | **305×** |

状态数上界 `2|L| + |R| + 2` 在所有测试族上**违反次数 = 0**。

`n=100000` 时全状态是 2.5×10⁹，实际只访问了 12 万 —— 这就是「删掉没用状态」的威力。

## 能带走的方法论

1. **DP 优化的本质是砍状态数**：总时间 = 状态数 × 单次转移。要么减状态，要么减转移代价。
2. **「一直顺路」的连续过程可以整个跳过**：用二分/单调结构一次跳到下一个决策点。
3. **换个度量衡可以消掉一个维度**：`S(x)` 把「时间最小」换成「进度最大」，时间维度就没了。
4. **看到「区间长度求和」就该想裂项相消**：分情况切分之后，求和自动只留首尾。
5. **启发式是猜，证明才是答案**：作者一开始只是用启发式搜索剪枝，剪出来才回头补的证明。
